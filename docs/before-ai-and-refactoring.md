# PR #1 の直前と #47 の整理を比べる

比較の起点は、PR #1 の直前の [コミット 6e00edc](https://github.com/sytkm/nonogram/tree/6e00edce3ffae40fd054fd085d0e78b15f9a428d) です。当時は、パレット形式PNGを開いてノノグラムを遊ぶ小さなアプリでした。アプリのJavaScriptは `importfile.js` が634行、HTMLは31行、CSSは35行でした。PNGを読み、盤面を描き、色を選んで答えを確かめる流れが一つのファイルで追えることは、当時の規模に合っていました。

機能追加が進むと、同じ `importfile.js` が2,044行になりました。JPEG・WebPやプレビュー、保存、共有などの追加で行数が増えたこと自体は自然です。#47で改善したのは、一つの機能を直すときに、離れた処理やページ全体の変数まで知らないといけなかった点です。

## PNGの幅を合わせる

[当時のコード](https://github.com/sytkm/nonogram/blob/6e00edce3ffae40fd054fd085d0e78b15f9a428d/importfile.js#L220) は幅が奇数なら行の末尾を1つ削っていました。

```js
if (pngwidth % 2 === 1) {
    row.pop();
}
```

PNGでは1バイトに複数画素が入ることがあります。たとえば2ビットで幅5なら、2バイトを展開したときに8画素分出てくるので、1つ削っても幅7です。ここは [PR #1](https://github.com/sytkm/nonogram/pull/1) で「指定された幅だけ取る」という、その後も通用する手順に直しました。

```js
pngmatrix.push(row.slice(0, pngwidth));
```

#47ではこの処理を [パレットPNGの復号器](../js/image/indexed-png.js) へ移しました。処理自体も、チャンク長を読むときにバイト列をコピーして逆転する手順から、`DataView` でPNGのバイト順を指定して読む形に変えました。どこからも読まれていなかったCRC値の取り出しを除き、色一覧を作るループの変数も関数内に閉じました。幅の修正はPR #1の機能修正、#47の変更はその後の挙動を保った内部整理です。

## 選んだ色を管理する

[当時の `drawUnderPalette`](https://github.com/sytkm/nonogram/blob/6e00edce3ffae40fd054fd085d0e78b15f9a428d/importfile.js#L489) は、色をキャンバスに描いてクリック座標から区画を算出し、他の処理も参照する `g_selectcolor` を書き換えていました。色の選択肢を実際のボタンにしたのは、#47より前の機能改善です。

#47では、選択中の色を [パレットを作る関数](../js/board/board-palette.js) の中へ移し、盤面側には色を選ぶ `selectColor` と、現在の色を読む `getSelectedColor` を渡す形にしました。次の区画を開くときは、その区画用のパレットを作ります。「今の色を誰が更新するか」が明確になり、盤面側が画面全体の変数を直接書き換える箇所がなくなりました。

## 保存と共有を分けて読む

PR #1の直前には、プレイ途中のブラウザ保存機能はありませんでした。機能追加後の保存コードでは、保存対象の関数・ID・共有元・日付を別々の変数に持っていました。#47では [保存コード](../js/play/progress-store.js) でこれらを1つの `progressSession` にまとめ、ページを離れた場合と非表示になった場合に同じ保存手順を使います。

[共有コード](../js/puzzle/mosaic-share.js) では、URLを開いて圧縮データを展開する処理と、復元したデータの検証を分けました。たとえば「全行の幅が同じか」という条件を調べるには、データの検証だけ追えば分かります。保存される形式と共有URLの形式は維持しています。

## なぜHTMLとCSSはこの粒度にしたか

通常問題と分割問題の共有欄は、見出しやリンク先の種類が違いますが、構造は同じです。両方で使うボタン、結果メッセージ、手動コピー欄をHTMLの `<template>` にまとめました。通常・分割で異なる説明はHTMLに残しています。

CSSは作成画面、プレイ画面、ダイアログ、分割一覧の4つに分けました。色見本のスタイルのように同じ要素へ離れた場所から指定していたものは、1か所で読めるようにしました。全体の行数を大幅に削る変更ではなく、修正するときに探す範囲を狭める変更です。

次に整理するか判断するときは、**同じ状態を複数の場所で更新しているか、同じ画面を作るコードが重複しているか、変更したい機能の入口をすぐ見つけられるか**を目安にできます。盤面の入力処理は、履歴やジェスチャーと同じ状態を見ているため、まだ大きなまとまりが残っています。分ける場面では、渡す値や責任がはっきりする境目から始めると、行数だけを基準に切り分けるより追いやすくなります。
