# パズル画面の追加・移行の共通仕様

新しい遊び方の追加、既存の遊び方のページ分離、複数の遊び方が使う画面・保存・共有の変更に適用する。着手時に影響する項目と試し方を決め、確認用PRに結果と未確認の範囲を記録する。過去の実装例は [複数の遊び方の構想 #3](https://github.com/sytkm/nonogram/issues/3) と [コードの構成](code-organization.md) を参照する。現行版の確認結果は [着手前の品質点検](puzzle-quality-review.md) に記録した。

## 着手前に決めること

- 遊び方ごとに `docs/puzzles/` に個別仕様書を作る。個別仕様にはルール、入力、例題と正解、実装する範囲、受け入れ条件を書く。着手時に確定した項目に沿って実装し、実装PRから参照する。[数字で塗り絵のたたき台](puzzles/paint-by-number.md)
- 最初に出す遊び方を一つ選び、開始からクリアまでの目標、入力、クリア条件、途中終了時の扱いを記す。複数解を認めるか、行き詰まり・不正な入力・出題できない画像をどう扱うかも決める。
- 初回に必要なものを決める。画像読み込み、サンプル、日替わり、共有、途中再開、分割、ヒント、時間計測は、採用した機能についてだけ条件と確認手順を書く。既存機能との違いは実装前に見えるようにする。
- 共通の操作と、ゲームのルールで決まる操作を分ける。例えば「元に戻す」が何を戻すか、再開後も履歴が必要か、時間をいつ計測するか、答えを見ると何が起こるかは、遊び方ごとに決める。
- 依頼者からは、遊び方の名前、簡単なルール、最小の問題と正解の例を受け取る。初回に必須の機能や既存の遊び方との違いがあれば確認する。画像を使う場合は、自作または公開利用できる画像を一枚用意するか、自作の仮サンプルで始める。検証用の大きな問題、異常データ、端末別の確認手順は開発側で用意する。

## 画面と文言

- 最初にすべきことを上の方に置く。ホームからサンプルまたは作成に迷わず進め、プレビューからすぐに遊べるようにする。作成者向けの検査・変換と、受け取り側の操作を区別する。作成者が試しに遊んだあとでも共有できる導線を確保する。
- 紙のパズルの罫線や余白を手掛かりに、色、書体、線、押した状態、フォーカスの表現を揃える。ボタン、タブ、設定の切り替えは見た目と操作で区別できるようにする。よく知られたアイコンか短い文言を使う。ノノグラムでは「元に戻す」「やり直す」「ヒントの数字」のように、対象と結果が伝わる言葉に揃えた。
- 頻繁な操作は盤面に近く、設定や最初からやり直す操作はメニューなどに置く。現在のモードや選択は、該当する操作を押す前にわかるようにする。ゲーム中に開く補助メニューは盤面やボタンを押し上げないよう、必要な位置に重ねて開く。
- スマホでは縦・横とも盤面を優先する。同じパレットを使う場合は狭い幅でも枠を2行以内に収め、色を選ぶ横幅を確保する。色が多いときは端の色まで移動できることを示す。操作のためにスクロールした場合でも、目当ての色・マスを選べるかを試す。
- 盤面を見ればわかる見出しや説明を常時表示する必要があるか見直す。操作名を画面・遊び方・確認メッセージで統一する。遊び方は基本、必要な操作、ヒントなどに分け、各ボタンの結果を短く説明する。頻繁に使わない補足は遊び方に置く。言語を増やす場合は、先に原文を揃える。
- 通常の案内は、閉じるボタン・外側タップ・Escで閉じ、フォーカスを元の操作に戻す。遊び方のタブを替えてもボタンの位置が動かないようにする。準備や破棄確認など、閉じ方を制限する場面は理由と復帰手段を確かめる。クリア画面には次にできる操作をまとめ、閉じたあとも盤面を見て結果を再表示できるようにする。
- 共通の見た目を変えたら、ホーム、作成プレビュー、通常プレイ、分割一覧・区画、クリア、設定・遊び方・確認・準備中を一通り開く。見た目に加え、開閉、フォーカス、余白、押した状態まで確認する。

## 入力と盤面

- 開始時・再開時・やり直し時に盤面が見えることを確かめる。拡大縮小がある場合は、等倍・全体の意味、倍率の限界、操作後の位置を一貫させる。状態が変わらない操作は選択中や無効として見分けられるようにする。
- 同一の操作がタップ、スクロール、ドラッグ、ピンチと競合しないようにする。ノノグラムの描画面では、なぞり塗りのオン・オフを問わず2本指の移動とピンチができること、指の本数を切り替えても誤入力しないことを確かめる。盤面外でブラウザの拡大やスクロールを利用できるかも確認する。
- キーボード操作では、フォーカスを可視化し、メニューから閉じたあとに操作へ戻れるようにする。色だけで区別が難しい状態には、記号・線・文言を併用する。パズルの仕組みに合わせて、盤面をキーボードで扱える範囲と表示を読み上げる方法を決める。
- 変更できないマスや結果閲覧中は、ポインターとキーボードの両方で編集できないことを確認する。停止中に盤面を隠すルールがあれば、入力と時間も止まることを確かめる。プレイ時間を記録する場合は、保存・再開、別タブや日付変更、クリア・ヒント・やり直しの扱いも確認する。

## 画像・保存・共有の互換性

- 画像を使う遊び方では、読み込み・画像処理の出力とゲームのルールを切り離し、同じ画素データを必要なゲームに渡す。パレット付きPNG、透過、写真、白黒・カラーなどの既存経路に影響する場合は、それぞれのサイズ・色・空白が元の仕様どおりかを確認する。変換失敗や上限超過では、原因と次に選べる操作を伝える。
- 既存の公開URLと共有形式は引き続き開けるようにする。GitHub Pagesの `/nonogram/` 配下で、ホーム、新規ページの直リンクと再読み込み、ブラウザの戻る、共有リンク、JS・CSS・Workerの読み込みを確認する。リポジトリの改名やURL変更は影響を確認してから別途決める。
- 保存・設定のキーは用途とゲームを区別する。変更時は公開済みデータで再開を試し、必要なら変換処理を用意する。通常・分割・日替わりを含め、遊び方の切り替えで別の保存を上書きしないようにする。保存対象を特定できる概要が見え、破棄や上書きの前に利用者が選べるようにする。
- 未保存、古い形式、破損、容量不足、保存拒否、無効な共有URLを試す。実行できる操作だけを表示し、再開できない場合にも元の問題を開き直せるようにする。初回専用の案内がある場合は新規プロファイル、再訪、保存拒否でも試す。共有URLの生成・コピーを使う場合は、安全な接続とローカルプレビューでの違いも確認する。
- 公開する問題や画像は自作または公開利用が確認できるものを使う。利用者の画像や認証情報は公開用の素材に含めない。外部素材・依存を追加する場合は、必要性、利用条件、配布方法を確認する。

## テスト・品質・リファクタリング

[ISO/IEC 25010:2011](https://www.iso.org/standard/35733.html) の「利用時の品質」の5項目を、以下の受け入れ確認に使う。[ISO/IEC 25010:2023の製品品質モデル](https://www.iso.org/standard/78176.html) と [ISO/IEC 25019:2023の利用時の品質モデル](https://www.iso.org/standard/78177.html) も参照できる。保守性、動作速度、保存の信頼性は製品側の確認にも含める。

| 観点 | PRで確認すること |
| --- | --- |
| 有効性 | ホーム、共有や画像などの採用した入口から入って、実際に入力しクリアできる。正解・不正解、固定マス、ヒント・時間のルールは例題で確かめる。 |
| 効率性 | 初めての人が少ない手順で遊び始め、頻繁に使う操作へすぐ届く。小さい盤面と現実的な上限に近い盤面で、開始・編集・拡大の待ち時間や操作の止まり方を比較し、測った条件を記す。 |
| 満足性 | 「最初にどれを押すか」「押すと何が起こるか」「クリア後に何ができるか」が伝わる。文言・盤面の読みやすさ・モーダルの使い勝手を試し、使い心地の判断は利用者の確認結果と区別して記録する。 |
| リスク回避性 | 意図しない編集・リセット・進捗の上書きや消失を防ぐ。保存や共有が失敗したとき、遊びを続ける、元の問題を開くなどの復帰手段を確かめる。 |
| 利用状況網羅性 | PC、スマホ縦・横、マウス・タッチ・キーボードで、対応範囲の操作を試す。実機、本番URL、ブラウザでの幅シミュレーション、未確認の状況を区別する。 |

- `node --test tests/*.test.cjs` と `git diff --check` を実行し、PRのCIを確認する。ロジックテストには小さい問題の正解・不正解、端や空白、代表的な異常入力を使う。保存・共有の変更時は、旧形式と新形式、保存失敗後の動作を検証する。再発を防ぎたい不具合には、修正前に失敗するテストを用意する。
- 画面変更ではPC、狭いスマホ縦（320px程度を含む）、一般的なスマホ幅、スマホ横で利用手順を通す。対象機能に応じてサンプル、画像作成、通常・分割、共有、途中再開も試す。タッチ固有の機能は実機での確認が必要かを明示する。
- 整理は影響するフォルダ・責務ごとにレビューできる範囲に分ける。既存の動作を確認してから、画像入出力、ルール、盤面描画・入力、プレイ状態・保存、共通UIの境界を見直す。重複や不要処理は、HTMLからの呼び出し、Worker等の間接参照、旧データの復元も調べてから統合・削除する。
- 状態の持ち主と保存形式を一つずつ決める。共有する関数や入出力の制約、旧データとの互換条件はJSDocかコード構成の文書に書く。HTML・CSSも同じ責務の単位で整理し、共通デザインとゲーム固有ルールを確認する。複数のゲームが実際に使う共通処理から共有し、既存のブラウザ標準機能を活用する。
- 振る舞いの変更、構造整理、ページ移行を独立して確認できるPRに分ける。著しい構成変更や実機の操作感に関わる変更は、公開前に試せる状態で確認を受ける。PRは日本語で、Issue・試し方・確認結果・未確認項目・対象を配信するプレビューを記載する。スマホ確認用のローカルIPは共有チャットに限る。
- 承認済みの公開では、Pagesのデプロイ結果を確認し、本番URLで直接開く。配信された変更ファイルをマージ済みの内容と照合する。次の作業を報告に添える。
